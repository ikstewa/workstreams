Orca project leads on the basecamp mod

How one person runs several projects in Orca, each with a lead session and its workers, once basecamp ships as the Claude Code mod described in the basecamp repo-context spec. It covers where a lead and its workers run, how Orca shows them, and what changes in the orca-lead plugin on the workstreams orca branch. It assumes that spec and does not restate it.

Orca behavior measured on 2026-11-09 in spikes against Orca's CLI and app. orca-lead read from the orca branch at 9c4b63a.

TL;DR

Each project lead runs in its own Orca workspace: a basecamp worktree created for the project. It has basecamp's full setup, and the mod gives it every team repo by absolute path, so it does not need the main checkout. The lead starts one worker per task with worker-start --worktree new-child in a worktree of the target repo's checkout under the mod's workPath. Orca nests each worker under its lead's workspace, so the sidebar shows one group per project. The orca-lead skill drops its "stay in the main checkout" rule and its own clone location, and keeps the Orca mechanics.

01

Goal

  • One sidebar group per project: the lead's workspace, with that project's workers nested under it.
  • Leads keep company-wide context to research across every repo.
  • Workers run with full Claude Code capabilities in the target repo's own checkout, as the basecamp spec makes standard for all repo work.

A lead's worktree holds only basecamp's tracked files, which used to be the obstacle: it had no clones. Under the mod that no longer matters, because every session reads the clones by absolute path in the main checkout (Appendix B). With a basecamp at ~/work/basecamp and the default workPath, repo checkouts land at ~/work/<repo> and Orca's workspaces under ~/work/workspaces/, matching orca-lead's current layout.

03

A project, start to finish

  1. Start the lead. Create a basecamp workspace for the project with its charter as the prompt (§02). It appears under basecamp in the sidebar.
  2. Research. The lead searches <basecamp>/.repos and reads team and repo CLAUDE.md files, as any session with the mod does.
  3. Prepare the target repo. If <workPath>/<repo> is missing, the lead clones it with gh repo clone; if Orca does not know it, the lead runs orca repo add --path.
  4. Start a worker per task with worker-start --worktree new-child. Orca creates the worktree, starts the agent, and nests it under the lead's workspace.
  5. Watch. Each worker's card shows its PR and checks. A follow-up, such as a review comment, goes to a fresh worker in the same worktree.
  6. Finish. When a worker's PR merges, remove its workspace with orca worktree rm --delete-branch. When the project ends, merge or drop the lead's basecamp branch and remove the lead's workspace the same way.

Changes on the orca branch

FileChange
skills/lead/SKILL.md Replace "stay in the home repo's main checkout, never an Orca worktree of it" with "run in the basecamp workspace created for your project". Take the clone location from the mod's workPath instead of WORK_DIR. In Orca, worker-start is how the separate repo session starts, in place of the mod's "give the person the command". Keep the rest: register each clone with Orca, one worker per task, stop and ask on a worker's trust prompt, a brief that says what to do when the fix is unnecessary, workers do not start workers, follow-ups go to a fresh worker in the same worktree, never type into a busy agent.
setup/orca-setup.sh Take basecamp's path as its argument, register basecamp with Orca, and read the work folder from the mod's workPath; drop WORK_DIR. Keep the skill install, the gh protocol, and the printed trust-prompt and plugin-install steps.
README.md Say the plugin requires the basecamp mod, installed and set up first.
SETUP.md Unchanged. Orca's workspace directory stays ~/work/workspaces.
05

Decided and open

Decided

  • Each project lead gets its own Orca workspace, with its workers nested under it.
  • The work lands on the workstreams orca branch, after the basecamp mod exists.

Proposed here

  • The lead's workspace is a basecamp worktree (§02).
  • Workers run in worktrees of each repo's own checkout under workPath.
  • The sidebar's card nesting is the per-project view; no plugin panel.

Open

  • Whether the old workstreams plugin (its board, project and micro-manage skills) is retired once this works.
  • Whether a lead's basecamp branch is worth keeping for docs, or leads write no docs and the branch is dropped by default.
