Spec · concurrent sessions

Workstreams and a control session for concurrent Claude Code sessions

About five Claude Code sessions run in this checkout at once, on different efforts and different repos, and the person running them is the only place their combined state exists. This document designs an opinionated way of working over Claude Code's own background-session machinery: workstreams with charters, one control session, one active session per workstream that a click reopens and a reset replaces, work delegated to sub-agents, and a board that answers "what now". It is opt-in and adds no runtime. It does not propose a daemon, a GUI, a second application, or a task queue that duplicates an issue tracker.

2026-09-18 · Ian · SPEC · Sources: this repository, Claude Code 2.1.276, 2.1.277 and 2.1.285, the code.claude.com reference pages read on 2026-09-18, and live tests on this machine on 2026-09-18, 2026-09-21, 2026-09-22 and 2026-09-23.

TL;DR

This is a convention-based workflow layer over Claude Code agents, not a system. Claude Code already provides the machinery: background sessions with dispatch, a switcher, needs-input state, stop, retire and resume; session names and a registry; cross-session messaging; hooks that inject context at start; phone push. A project's memory already keeps a file per unit of work. The layer adds conventions: the workstream as the unit, with a charter of purpose, scope, focus and goals; one control session that belongs to no workstream; one active session per workstream, dispatched in the background, foreground only while Ian talks to it, reopened on a click even after Claude Code retires it, and replaced only when Ian resets it from its row; work in sub-agents and workers; the record synced every substantive turn. The code is one hook, one mod, one skill, ten lines of statusline. It ships as an opt-in plugin so nobody else's sessions change.

Built

  • Charter frontmatter on the per-workstream record, moved out of memory/.
  • One mod: the charter as a row of the bound session's conversation, at start, after /clear and after a compaction; the charter tool, the bound session's one way to write its charter; goal sync with the task list; and every session's board record, from the engine's own session, turn, tool and sub-agent events.
  • One hook: the record's state machine the mod drives, the charter writes and goal sync it runs under one lock, the record-sync hold, the board render the skill prints, and the sidebar click that reopens or resets a row's session.
  • One skill: prints the hook's board render, then ranking, charter interview, dispatch, stop and sweep.
  • A statusline count of sessions waiting with a live process behind them, and the statusline writing context size back to the record.

Not built

  • A daemon, queue file or second application. The live board is a read-only redraw loop over files the hook writes.
  • Planning and orchestration as separate roles.
  • Replacing a cold session on its own, or holding the prompt typed into it.
  • Terminal tabs as the switcher.
  • Agent Teams, a polling loop, an approval relay, a per-prompt alignment call.
01

What the layer adds over the agent view alone is grain and judgment. The agent view knows sessions and their states. The layer knows workstreams, charters, what changed overnight, which session is cold, and what to pick up next.

02

Workstreams and charters

The unit of work is a workstream: a named effort that runs through many sessions, usually several tickets, and often several repos, over days or weeks. Ian's memory index already declares forty-odd of them by hand, one file each, some keyed by ticket and most keyed by topic. The design makes that declaration explicit and gives it four fields.

A workstream is defined by declaration, not by Jira structure. Its charter has:

  • Purpose. Why it exists, one sentence. Required.
  • Scope. What is in and what is out, two short lists. Optional at birth, drafted by the agent from the first session.
  • Focus. What it is on right now. Rewritten as it moves; the agent proposes, Ian accepts.
  • Goals. What finishing means, as an ordered checklist of [ ] and [x] lines under goals:. Required. Each goal is mirrored on the active session's task list: completing its task ticks the goal, and the session adds a goal through its charter tool (§4) when new work appears. Every goal ticked is the stopping condition, and the board then proposes closing the workstream (§8). A dormant row shows what is left: all done, not started while no session has taken a turn, N goals left, or no goals for a charter that has none yet.

A block, while one stands. When the work waits on something outside the session's control and not on Ian, such as a review, someone's feedback or a merge, the workstream's session sets two more fields through its charter tool (§4): blocked:, what it waits on, free text, quoted or not; and blocked_since:, when it began, as YYYY-MM-DDTHH:MM:SSZ. The session removes both once the block clears, and nothing else clears them. They live on the charter so that they outlive a retired or reset session, and a session picked up or reopened with a block set first checks whether it still holds. blocked: without blocked_since: is still a block, shown with no age; an empty one is none.

A note, while Ian has one. note: is a line of Ian's own on the workstream, free text in double quotes, set and cleared from the sidebar (§9). Nothing else writes it, and the session reads it with the rest of the charter.

Plus a references list that accumulates on its own: tickets, epics, PRs, docs, repos. Tickets are references inside a workstream, not a level of it. A workstream with several deliverables whose tickets close at different times is the normal shape, not a signal to split.

The charter and the record live in one file per workstream, ~/.claude/projects/<slug>/workstreams/<KEY>.md: the charter as frontmatter, the handoff as the body. Today that content is a project-<slug>.md memory file, written by the skill chain at milestones and read by a ticket skill on resume. It moves out of memory/ on purpose. Anything under memory/ is indexed into every session and eligible for recall into any of them; a workstream's record is relevant to exactly one session, the one bound to it, plus control. The workstreams/ directory is a sibling of memory/ and board/, so nothing there is indexed or recalled, and the mod appends it where it belongs.

The memory index shrinks. MEMORY.md loads into every session, and its Active projects section is its largest block: a dense hook line per unit of work so that any session can pick any of them up. Once the records move, that section goes with them. The bound session gets its charter and the newest part of its record at start; control sees every workstream, live or dormant, on the board; no other session needs to know. Memory keeps what is general: who Ian is, how he wants work done, references. A one-off migration moves every existing project memory file into a workstream record, and the board's sweep repeats the move for any project file a skill creates afterwards, so the leak does not reopen.

Two ways a workstream starts. A director-level one starts with a short interview in any session: purpose, scope and goals. A ticket that no charter cites gets a one-ticket charter derived from the ticket with no questions: purpose from the summary, scope equal to the ticket, and one goal, the ticket at Done. The ticket skill gains one lookup: which charter cites this ticket, so "work on PROJ-12" lands on the workstream that owns it rather than starting a new one.

Alignment, in three layers, none blocking. At session start the bound workstream's charter reaches the session with one instruction: when a request falls outside scope, say so and offer to extend the scope, do the work unattached, or start or attach to another workstream. The model already in the session does the judging at no extra cost. Structural checks in hooks need no model: a worktree entered for a repo not in the references, a ticket touched that no charter cites, a second active session on one workstream. Each produces one advisory line. A semantic pass runs on demand in the board's deep mode, reads each workstream's recent activity against its charter, and proposes a fresher focus line or asks whether a request belongs elsewhere. Splitting is Ian's act, prompted only when a request does not serve the stated purpose. Workstreams do not nest; charters link to each other, and Jira initiatives already render as the umbrella.

An idle workstream is one whose record has a non-terminal status and no live session. The board groups by assignment, by block and, with nothing live, by goals (Active, Blocked, Idle, Unassigned, Done); a session's status colours its row and moves it only between Active and Blocked, or Active and Done for a finished workstream (§6). A done workstream stays on the board, labelled done, while a session of it is still live, in Done unless that session is working or asking Ian (then Active), and leaves the board when none is. It appears on the board with its last handoff, which is how work Ian started and closed the tab on stops being forgotten; after three quiet days it is stale instead, and the board carries its name rather than its handoff (§6). This is the one place persistent memory is load-bearing for tracking: the record is the workstream between sessions.

03

Control

Control is one session, named control, that belongs to no workstream. It is the only session Ian keeps in the foreground by default.

Control owns the workstream level and the cross-workstream policy:

  • Creating and editing charters: the interview, attaching tickets, writing the goals, and closing a workstream once they are all ticked.
  • Dispatching active sessions and workers, stopping them, sweeping retired ones that no row reopens.
  • The working limit and the ranking policy.
  • The board.

Control holds no state. Every answer is re-derived from the records, the registry, and on request GitHub PRs and Jira. Forwarded events are one line each. Ian can /clear it at will; the name survives, and the next board rebuilds the picture. A session is control by its name, control, which is also how other sessions address it as @control.

Control never plans a workstream inside itself. Forty minutes of one workstream's design would fill its context and make it a member instead of the reader. It dispatches the workstream's active session and stays out of it.

04

The active session

Each workstream has at most one active session. It does whatever the workstream needs right now: in the foreground it talks to Ian about the plan; in the background it works the plan through sub-agents and workers. It is the same session either way and flips between the two with ← and Enter. Planning and orchestration are not separate roles; once execution is delegated, a conversation about the plan and the coordination of its execution are the same kind of content and both fit in one small session.

Naming binds. The session's name is the workstream key: PAYMENTS_API. The plugin finds the session's registry file by its session id, reads the name there, and looks up the charter that carries that key. For a workstream Ian starts by hand, /rename mid-session binds on the next prompt. Claude Code renames a second interactive session that takes a live name, so a duplicate active session announces itself; for background sessions the name is not deduplicated at startup, and the board flags the duplicate from the registry instead.

The charter arrives as a conversation row. The plugin's mod appends it to the session's conversation as a user row, which the model reads and Ian does not see as typed. The row opens with the charter file's path and the operating rules, so no length limit can cut the rules off; then the frontmatter, whole; then the record, cut to its newest 30,000 characters at a line start, with a line naming the file when its start is left out. A fresh session gets that full row. A resume, a reopen or a reload, whose transcript already holds a charter row, gets a refresh: the path, the rules and the frontmatter, which carry anything Ian changed meanwhile, without the record the session already holds. After /clear the full row lands ahead of the next prompt. After a compaction of the main conversation the full row follows at the next prompt or model request. On each prompt the mod reads the session's registry file, and a new name from /rename appends that workstream's charter. A session bound to no charter gets no row, and a failure appends nothing and writes one line to the debug log.

The session writes its charter through one tool. The mod registers mcp__workstreams__charter whenever board.py finds the session bound: at start, after /clear and on a /rename. An unbound session never has it. One call carries any of five fields: focus, set on one line where it stands; record, one entry appended to the record as a top-level bullet led by a bold date unless it brings its own; add_goals, each new goal appended open with its task mirrored at once, and a goal already listed skipped; block, which sets blocked: and stamps blocked_since: in UTC; and clear_block, which removes both. Values are written double-quoted and escaped, so quotes, backslashes, colons and # read back as written. No field reaches note: or a goal's checkbox: a tick stays on the task list, because the session's own task call is what opens Ian's task panel. The mod answers the call itself, so core never runs it and it asks for no permission in any mode; a sub-agent's call is refused. The write runs board.py write on the mod's one queue, behind the record's events, and the call waits for that write alone. A refusal, a failed run or a timeout reaches the model as an error that says why. The tool is deferred, so the operating rules name it and tell the session to load it with ToolSearch. The rules say when to write; the tool's description says how.

Goal sync runs from the mod. It mirrors the charter's goals onto the task list at a start, at each prompt, at each main-loop turn's end, and for the id a /clear or /resume goes on under. Once a TaskUpdate has run, it ticks that task's goal from the task's file. Both run board.py on the same queue, so two updates made in parallel tick one after the other. Every read, change and write of a charter, the tool's, a tick's and Ian's note from the sidebar, holds one lock beside the charters, so none writes over another. No settings hook remains: a session started before that change keeps its old ones until it reloads, and they now read nothing and print nothing.

Operating rules, stated once in the dispatch prompt and reinforced by the charter row:

  • Work through sub-agents and workers; hold coordination only.
  • Every substantive turn, add a record entry and set the focus (plan progress, in flight, next) with the charter tool, never by editing the file.
  • Keep the charter's goals current: completing a goal's task ticks it, and new work becomes a new goal through the tool.
  • When starting on a goal, set its task to in progress. Claude Code opens the task panel only on the session's own task write, or a saved showExpandedTodos that any session with an empty list turns off again, so goal tasks the mod writes stay folded until then.
  • Report to @control; ask before any push.
  • The workstream is private to the machine: never mention it, its charter, goals, record or block in a commit message, PR, ticket, comment or document, because no reader there can see them; state what the work is for in its own terms, cite a key that is also a ticket key as that ticket, and tell any sub-agent that writes these the same.
  • When a request falls outside the charter, say so and offer the three exits.
  • When the work waits on something outside the session and not on Ian, set a block with the tool, and clear it once it clears; picked up or reopened with a block set, first check whether it still holds.
  • The charter's note: line is Ian's own: read it. The tool cannot change it.

The active session is disposable. Dispatch starts it. claude stop from control ends it. Claude Code's supervisor retires every settled background session that is neither attached nor pinned once it has had no input for 60 minutes, a session waiting on a question included: it reaps the process and removes the registry file. That is Claude Code's behaviour, not the board's. A retired session stays in claude agents --json --all with no pid, and claude attach with the first eight characters of its session id revives it under the same session id, with its whole transcript; the session starts again, so its board record continues. claude rm takes it out of the listing, and then nothing can revive it. Between one session and the next the record carries the state, and a session ends with its record current because capture is continuous, so a shutdown at any moment loses nothing.

A click reopens; the reset button replaces. A click on a sidebar row opens that row's own session and never a new one: a live session is attached as it stands, and a retired one still in the listing is revived. An Idle row carries its workstream's latest active session, by last turn and else by start, and a click dispatches a fresh session only when that session is gone from the listing or there never was one. The prompt cache on this plan lives one hour. A session whose last turn is older than that is cold: reopening it re-sends the whole conversation uncached, and an 80k-token transcript is common by mid-afternoon, while a fresh session starts from the charter, the handoff, the plan and any worker results in about 6k tokens. So a cold row of a charter's active session, whose turn is Ian's, shows ↻ as its status glyph; a click on it stops the session if it is live, dispatches a fresh one with the same name, and opens that. Working rows, rows waiting on a permission or a question, warm rows, control, workers and unassigned sessions, which have no charter to start fresh from, and an Idle or Blocked row with nothing to reopen, whose click already starts fresh, never carry it. A Blocked row (§6) shows ⏸ while its session is fresh and ↻ by these same rules once it is stale, so a fresh session can be started once the block clears. The click checks again, so a session that has turned busy or started asking Ian since the redraw is only opened. A dispatch holds its workstream for 15 seconds after claude --bg returns, so the second click of a double-click starts nothing. Claude Code's own resume-from-summary dialog compacts a transcript into a generic summary; the handoff is written by the session, structured, and lives where control and the board read it.

A hold enforces the convention a prompt cannot. A Stop hook holds the turn with one line when sub-agents have finished since the record was last written and the turn is ending without a sync. It is advisory in effect and costs nothing. No prompt is ever held.

05

Workers and sub-agents

The active session does not do the work. In-process sub-agents take short synchronous tasks; they die with the active session, and the board lists them only while they are running: the end of a sub-agent's run removes the row. A turn that ends with one still running shows as Working, not unread: the session waits on the sub-agent. Background workers are sessions of their own, named <WORKSTREAM> work: <task>, for anything that should outlive the active session: a forty-minute test run, an integration suite, a long build. They report to the board and to control, and to the active session only while it is live; they never wake a retired session. A worker's permission prompts show under Needs input like any other session's.

Dispatching a worker goes through control so the naming stays in one place. The active session may ask control for one by message.

06

The board

The board is a directory of small JSON files, one per session keyed by session id, plus control.json, at ~/.claude/projects/<project>/board/. Every session in a project and any of its worktrees resolves to that directory: board.py strips the /.worktrees/… suffix from the project path to reach it. It is outside the repository, so a worktree write guard and the repository's .gitignore do not apply; it is per machine and per user, which is the scope of a session; and it is a sibling of memory/, not inside it, so nothing on the board is recalled into context.

A record carries the session id and pid, the workstream from the name, whether the session is the active one or a worker, cwd and repo and branch, state (busy, idle, waiting, ended), what it is waiting for and since when, the last assistant message truncated, its children with their states, context size and cache warmth written by the statusline, and timestamps.

Registration is involuntary. The mod writes the record from the engine's own events, one board.py event run per transition (§7). The runs queue in the order the events come and run one at a time from a timer of the mod's, so no hook waits for one, and a hook whose dispatch is abandoned, as an Esc at a dialog abandons it, cannot stop one; only session.end waits, inside its short bound, since an exit follows. It finds the session's identity, its name, pid and workstream, in the registry file that names its session id. A session does not declare itself; the mod runs in every session that loads the plugin, so a session that forgets the naming convention still appears, under its derived name, flagged as unassigned. It forwards an event only after the engine has decided it and changes nothing it passes on, so it can never alter a permission decision. The plugin keeps no settings hook: goal sync runs from the mod too (§4).

Liveness comes from the operating system. A record whose pid has no registry file is dead, whatever it says; and a registry file alone does not make one live, because removal is not synchronous and the file outlives a killed session by anything from seconds to tens of seconds. Live means both: a registry file, and a process answering to that pid. The design adds no lease and no heartbeat of its own; the registry keeps one already. Records for ended sessions are pruned by the skill after seven days.

claude agents --json is not that authority. It keeps a background session that died while listing blocked, so a row there reports state, not life. It is read for two things only. A waitingFor it names while it lists a session blocked draws that session red, as an ask: the engine's own word for a dialog the mod sees no tool check for, such as an MCP elicitation. And a retired session it still lists as a background session is one a click revives (§4). It is never read for liveness, for a reply or for whether a turn is running. Where the board and the agent view disagree, the board is the more accurate of the two, not the fallback: a workstream whose session died while listing blocked renders as a dormant row, which is correct, while the agent view still shows that session under Needs input.

A turn counts as running by the record. A live session is working while its record is busy or a sub-agent of it runs. The mod sets busy at the start of every main-loop turn, one begun without a typed prompt included, such as a task notification, a peer's message or a sub-agent's handback. Every turn's end clears it: an answer, a refusal or an error leaves a reply waiting on Ian, and an interrupt settles the record at once. So an interrupted session reads as settled, with its hours and, once it is cold, the reset button (§4); a running one draws Working and a reset leaves it alone. A reply whose sub-agent still runs draws Working too: the session waits on the sub-agent. The registry's status, the job file and the listing are not read for any of this.

Blocked sits between Active and Idle, and holds only what is not Ian's move. A workstream whose charter carries a block (§2) shows there with its key and a dimmed label of what it waits on and for how long, PR #12 · 2d: minutes under an hour, hours under two days, days after. In the sidebar the label may take half the row and the name truncates first; past half, what it waits on truncates before its age. Anything Ian can act on outranks a block: a session of the workstream that is working, or waiting on a permission, a question or any wait but a reply, shows in Active exactly as it would without one, green or red. A reply, read or unread, a settled session, a retired one or none puts the row in Blocked. A click on it does what a click on that session does: it attaches the live one, revives the latest retired one, or dispatches a fresh one when there is none. Its glyph is ⏸, and ↻ once its session is stale (§4). A Blocked row carries no need, so Option+n passes over it (§9).

Done is the last group, after Unassigned, and holds only what has nothing left. A workstream with no live session whose charter has goals, every one ticked, shows there labelled all done instead of in Idle, so Idle holds only rows with work left. Its row is an Idle row in every other way: its glyph is ◌, and ↻ once its session is stale (§4); a click reopens or dispatches; and it carries no need, so Option+n passes over it (§9). A live session of a charter whose goals are all ticked stays in Active, because its status is Ian's move; a block keeps the row in Blocked; and a row whose last turn is three days old still collapses into the stale line. A Done row is the board's proposal to close the workstream (§8). A status: done charter with a live session shows there too, labelled done, unless a session of it is working or asking Ian, which keeps it in Active. Such a row keeps its session's glyph and colour and its need, so Option+n still reaches an unread reply or an ask.

A workstream nobody has worked on lately collapses to one line. The board renders every workstream whose status is not done or archived, two lines apiece, and there are forty-odd of them once the project memory files have all become records — a list as long as the memory index it was meant to replace, and as little use. A board that lists everything is not a board. So a workstream whose last session turn is more than three days old, and which has no session record at all, is left out of that list and counted on one line at the end of it — unless the charter itself was written within those same three days, which is what keeps a charter that has just been written on the board, one dispatch away, instead of reading as abandoned before its first session: stale (38, no session in 3d): PAYMENTS_API, PROJ-31, PROJ-44, … — every key, alphabetical, however many there are, since a sample would leave Ian wondering what else was on it. When nothing is stale the line is absent, and the workstreams that remain render exactly as they did. Three days measures a workstream and is not the hour of §4, which measures a session: a session goes cold when its prompt cache expires, a workstream goes stale when no session has taken a turn on it in three days and it was not itself written within that window.

Staleness is measured from session activity and from the charter's own birth date, never from the record file. It is the most recent last_turn_at across the board records carrying the workstream's key — the last time a session did work on it — and where no record names the key at all, that is not enough on its own to call a workstream stale: the charter carries created:, a plain YYYY-MM-DD a person writes once by hand when the charter is authored, and a charter created within three days renders in full even with no session ever bound to it. A full ISO timestamp would be noise in a file a person edits by hand, so the field stays a bare date. A workstream is stale only when all three read old together: no live session, no last_turn_at within three days, and no created: within three days — any one of the three is enough to keep it rendering as a row. A block keeps the row too, however old the rest reads: a blocked workstream never collapses into the stale line, because its row is where the block's age shows. The record file's own modification time was the obvious place to read a birth date from instead of adding a field, and is the wrong clock for the same reason it was rejected for last_turn_at: a migration writes forty-odd charters in one pass, so every one of them would carry today's mtime and the whole list would render fresh for three days, then collapse in a body on the fourth. A hand-authored created: does not move when a bulk pass touches the file, so it is safe where mtime is not, and nothing about what a migration writes has to change for it to work. A live session wins outright regardless of any of this: staleness is computed only where nothing is live for that workstream, so a session dispatched a minute ago, which has taken no turn yet, is never read as an abandoned effort. A last_turn_at or a created: that cannot be parsed counts as old — stale-eligible — the same as one that is simply absent: a date that cannot prove a charter current must not manufacture a row that should not be there, so a key on that line can mean a record that is broken rather than a workstream that is quiet.

Stale is a rendering state, not an ending. A workstream can be legitimately untouched for a fortnight, so nothing sets status: archived on its own; the skill proposes the stale set and Ian confirms. The collapse costs nothing and undoes itself on the next turn a session takes against the workstream.

Reaching control without polling. The hook reads board/control.json, checks the pid is alive, and writes one line to control's inbox socket, whose path is in the registry. Under the default inbound rule, auto mode is the prompting class and a raw line claims no permission class, so it is delivered without a dialog; if control is idle, the line starts a turn, which refreshes the board and calls PushNotification when the event is one Ian would leave his chair for. The socket's line protocol is documented only as far as the auth line and a probe was denied by the auto-mode classifier in this session; it is the first spike. Fallbacks: notify_when_idle subscriptions from control, which cover "finished" but not "waiting"; and the agent view itself, which moves a waiting session to Needs input with no help from this design.

Approvals cannot be centralised. Claude Code treats a message from another session as untrusted input and never as consent. Control names the session and how to reach it; the approval happens there, or on the phone through Remote Control. Decisions, as opposed to approvals, travel fine as messages: the active session asks control by name, Ian answers in control, control relays.

08

Guidance

Control's first turn is the board. Control is dispatched on demand, from the sidebar's Control row or Ian's launcher, with /workstreams:board as its first prompt; it gets no charter. A click on the row opens a live control as it stands, and replaces one that is gone or cold. The board reads local inputs only: the board records, the session registry and the workstream records. It says which sessions are waiting and for what, where each workstream worked in the last three days was left with its last handoff, how cold its last active session is, the rest of them on the single stale line (§6); control adds a ranked "what now". The board calls nothing outside this machine: no gh, no Jira. What changed overnight in reviews and CI is a separate operation, run deliberately (below). The board is also the inbox for events that arrived while no control was running: nothing is forwarded, but every event still reached its record.

Ranking, highest first, each with its reason stated:

  1. A session waiting on a permission or a question, oldest first. It stalls a running worker and takes seconds.
  2. Something that changed outside: an approved PR, changes requested, a failed PR check. Someone else is waiting. It ranks only once the sweep has run.
  3. A finished session whose next step is a skill, such as completing the code or handling an approval.
  4. The workstream Ian was mid-flight on, reopened from its row, or reset to a fresh session from its handoff once it is cold.
  5. A dormant workstream with no goals, or an orphan ticket no charter cites. Both are scoping decisions; the board proposes, Ian chooses. A workstream whose goals are all ticked reads all done: the board proposes status: done, Ian confirms, and nothing closes a workstream on its own.
  6. Free capacity below the working limit: the sprint by priority.
  7. Housekeeping: claude rm for retired sessions no row reopens, such as one a reset has replaced, removing merged worktrees, and archiving the workstreams on the stale line that Ian agrees are finished.

/board reads local inputs only and answers in seconds. The board is one deterministic render function in the hook, board.py render: /board prints it verbatim, then adds its "what now" under a separate heading as the model's own judgment. /board --deep is the overnight sweep, and it is invoked, never automatic: it adds your open GitHub PRs and the Jira tickets charters cite, reports what changed in reviews and CI since it last ran, runs the drift check against each charter, and re-ranks. It takes as long as those calls take, which is why it is a deliberate act in the first turn rather than something Ian waits on at every session start. /board <WORKSTREAM> shows the charter, the active session with its children and context, workers, worktrees, tickets, PRs, the previous sessions by id, and the actions: message, open, stop, phone, edit charter.

Rules the skill honours because they are already recorded in the user's memory: ask before any push, and report external state that changed mid-session rather than repairing it.

09

One terminal

Every session other than control is a background session, so the agent view is the switcher: ← in any session shows Needs input, Working and Completed; Enter opens a row; ← again leaves it running. A session opened this way is in the foreground while Ian talks to it and in the background otherwise. The live board runs beside it in a narrow tmux pane.

The sidebar marks the row whose session is open in the right pane, with a bar in its first column. It marks a row only while board/open.json and the right pane's title name the same key, because the file outlives the pane: after a tmux restart the pane is rebuilt on the agent view, and the pane closes when its claude attach exits.

A click on a row opens its session in the right pane (§4). tmux passes the click's column with its line, and a click on a cold row's ↻ glyph, or the space after it, resets that session instead.

The keyboard switches too, from any pane, and focus stays where it is. Option+j and Option+k step to the next or previous session the sidebar can open without starting one: a live background session, or a retired one that a click revives. They follow the sidebar's order from the row open now and wrap at both ends, passing over any row whose click would start a session or only say why it cannot. Option+n opens the session that most needs Ian. Red rows come first, asking him for anything but a reply: a permission, a question, or what the listing says the session waits for, the longest wait first. Unread replies follow, the oldest first, dated by the wait or else by the last turn; a reply he has read is passed over, and so is every Blocked row, which waits on someone else. Control counts like any row. Like a step, it moves on from the row open now, so pressing again goes down the list, and it opens only a row whose click would attach; with nothing to open it says so. Option+m opens a menu of every row, and picking an item is a click on that row. Option+e notes the workstream open in the right pane (below). The bindings apply only inside the ws tmux session; elsewhere each key reaches the pane unchanged.

A note is Ian's own line on a workstream, for where it stands or that it needs nothing more from him. Option+e opens a prompt for the workstream open in the right pane, labelled with its key and holding its current note; Enter saves the line and an empty one clears it. With nothing open, or a session with no charter, such as an unassigned one or control, it says so and opens no prompt. The note is the charter's note: line (§2), so the session reads it with the rest of its charter. Only the prompt writes it, and only that line. The session writes its charter only through its tool, which never touches note:, and every charter write holds the charters' lock (§4), so none writes over the note. The sidebar draws a note as a dim line directly under its row, on the group's trunk and above the row's hint and sub-agents, once for a key with several rows; the wide board adds a note: line under the row. A note is display only: a row's group, colour, glyph, place in a step and click are what they would be without it.

The rows under the footer describe the workstream open in the right pane. Below the quota line, under a double rule, the sidebar draws that workstream's charter: its key and what is left of its goals, set off by a blank row above and below, then what it is blocked on (§6) and Ian's note, dim under ⏸ and ✎, then its purpose, then its open goals at up to two rows apiece, a blank row between each. The focus is left out: it runs too long to read in a narrow pane. It takes the rows the board leaves free and stops one short of the pane's last, which the watch's newline would scroll. What does not fit is cut, and the last row shown ends in …, so a taller board leaves less of it, and a pane with no room under the heading shows none. The agent view, control and an unassigned session have no charter, so with one of them open the rows stay empty.

A click on a goal asks the open session to work on it. Either row of a goal in the panel types Focus on this goal: <goal> into the right pane and presses Enter, so it reaches the session as Ian's own message, and a turn that is running queues it as it would anything he typed. The text goes in as a bracketed paste, which a vim-mode prompt takes as text even in NORMAL mode. It is never sent while that session asks Ian for anything, a permission or a question, since Enter would answer the prompt; a tmux message says to answer it first. Anything already typed in the prompt is sent with it. Every other row of the panel is display only, and a goal's rows are not stops for the keys or items in the menu.

bin/ws builds the ws session and applies every binding, and it applies them again on each run that reattaches, finding the sidebar and the right pane in the running session. A shell function that only calls it never holds a stale copy of the bindings.

The agent view lists background sessions and the current one. Interactive sessions started in other terminals do not appear in it, which is the second reason everything is dispatched as a background session. Programmatic switching does not exist: no hook output or tool changes what a terminal shows, and a slash command arriving from another session is plain text.

Tabs remain an escape hatch. Ghostty 1.3 ships an AppleScript dictionary, and three statements open a tab in the existing window running a named session or claude attach <id>. It was verified on this machine and is kept for "open this one for me now", not as the flow.

10

Packaging and opt-in

This is how Ian wants to work, and it must not be imposed on anyone else. Everything here is opt-in by construction and by packaging.

  • By construction. The hook acts only on a session named control or bound by name to a workstream charter. Every other session gets a board record under its derived name and nothing else: no injected context, no holds, no forwarding. The charter interview, the board and the dispatch recipe are skills invoked on purpose.
  • By packaging. The hook, the skill and the statusline snippet ship as a plugin, provisionally workstreams, enabled at user scope in ~/.claude/settings.json. A project's checked-in settings carry none of it. A contributor who does not enable the plugin sees no change; one who does gets it in every project, which is right, because workstreams are a person's way of working rather than a repository's.
  • Personal first. Nothing in the layer depends on a particular project except the memory store's location. If the plugin proves useful to Ian alone, its home is his own plugin directory; if to several people, a shared marketplace; the substrate stays where it is either way.
11

Decided and open

Decided

  • The workstream is the unit; its charter is frontmatter on its record file under workstreams/, beside memory/, never inside it.
  • Project memory files migrate into workstream records once, and the sweep migrates any new one; the index's Active projects section goes away.
  • Every charter has goals, and every goal ticked is its stopping condition. A charter without them is flagged, not refused; one with every goal ticked is proposed for closing, never closed on its own.
  • A block lives on the charter, set and cleared only by the workstream's session; anything Ian can act on shows in Active over it.
  • One control session, stateless, belonging to no workstream.
  • One active session per workstream, background by default, no roles.
  • A click reopens a row's own session and a reset replaces it; no prompt is held; capture is continuous; work lives in sub-agents and workers.
  • The agent view is the switcher; tabs are an escape hatch.
  • The issue tracker remains the queue; approvals stay where Claude Code puts them.
  • Opt-in, packaged as a plugin; a project's shared settings unchanged.

Open

  • The inbox socket line protocol.
  • Whether the Stop hook should hold a turn or only remind.
  • The working limit and the dormant threshold; defaults five and seven days.
  • Names: /board, /ws, workstreams are placeholders.
  • Whether the plugin's home is a shared marketplace or a personal plugin directory.

B

Rationale

The missing piece is a join and a set of habits, not a system

Identity, liveness, messaging, dispatch, switching and phone reach are each native and were confirmed on this machine. Retirement is native too: Claude Code's supervisor retires a settled background session after 60 minutes with no input and keeps it listed, where claude attach revives it. The workstreams, their sessions and their wait states are all recorded somewhere; nothing records them together, and nothing tells a session how to behave so that it can be thrown away. A join is a small file and a reader; the habits are conventions a hook can back.

The unit of work outlives the session, so the record must too

Ian's own index proves the grain: forty-odd efforts, one file each, most spanning several tickets. Keying on the session inverted what he tracks. Keying on the workstream makes a dormant effort visible with no session alive, which is exactly what was being forgotten.

Delegated execution is what lets one session hold both planning and orchestration

The separate planning and orchestration sessions of today exist because execution filled the orchestrator's context. Once the work is in sub-agents and workers, the active session holds coordination and conversation only, which are the same size and the same kind of content.

A click reopens because the transcript holds the working context, and a reset is one click away

A one-hour cache and an 80k transcript make reopening a cold session the expensive path, and a fresh session from charter, handoff and plan costs a twelfth as much. But the transcript holds what the record only summarises, and a session Claude Code retired while Ian was away is one he means to come back to. So a click reopens it, and a cold row's reset button leaves replacing it to Ian. A fresh session starts already knowing what the previous one decided only if capture was continuous. That is why the Stop hook backs the sync rule.

Registration must not depend on the worker cooperating

A queue-file tool forces a declaration because its workers are opaque processes. Here every session runs the same mod and every turn's end hands over its answer, so a design that relied on the session ending its turn with a status line would fail silently the day it forgot.

Approvals cannot be centralised, so the layer indexes them

Claude Code treats a peer's message as untrusted input and never as consent. Pointing at the right session and pushing to the phone is the whole of what can be built, and the agent view already lands the session under Needs input.

The agent view is the switcher because it is the only one that can be driven from inside Claude Code

No hook or tool changes what a terminal shows. The agent view is two keystrokes and shows every background session; tabs required an emulator-specific script and hid sessions from it.

Opt-in is a property of the packaging, not a promise

A plugin enabled at user scope changes only the enabling user's sessions, and a hook that acts only on bound names changes only the sessions that asked. Both are checkable in the code, which is more than a note in a README.

The issue tracker is already the queue with forced outcomes

A ticket cannot leave a session's hands without a status change, so a second queue would be reconciled against the first on every read.
