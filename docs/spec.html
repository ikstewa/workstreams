Workstreams: GitHub Projects, leads and workers for Claude Code sessions

The user runs several Claude Code background sessions at once, across several projects and repos. This plugin keeps each project's state on a GitHub Project board, runs one lead session per project to drive it, and runs one worker session per task. A tmux sidebar shows every project, its sessions and what the watch last saw.

2026-11-03 · SPEC · Sources: Claude Code 2.1.318, the GitHub GraphQL and REST APIs, and live tests against a user-owned GitHub Project.

TL;DR

A project is a GitHub Project (v2) owned by the gh user. Its README holds purpose, scope and the lead's settings; its cards are the work; its status updates carry focus and progress. Each project has one lead: a background session that moves cards, posts updates, and starts and closes workers. Each worker is a Claude Code team on one task in one repo, briefed from its card. A watch polls the board, PRs and tracker tickets and reports changes to the lead. The sidebar reads the watch's cache and the session layer, and never calls GitHub or the tracker itself.

01

The shape

State lives where people already look: on GitHub and in the tracker. Sessions hold none of it, so any session can be closed and a new one picks up from the board.

PieceWhat it isWhat it holds
ProjectA GitHub Project (v2) owned by the gh userREADME, cards, status updates
LeadOne background session per project, in its lead-repoIts conversation only
WorkerOne background session per task, a Claude Code team in one repoIts worktree and branch
WatchA poller started with the leadA throwaway local cache of last-seen state
SidebarA tmux pane on the leftNothing; it reads the cache and the session layer

The plugin ships four kinds of code:

  • A mod that injects a session's role instructions and registers that role's tools.
  • Launchers for leads and workers, which set the role env and strip inherited CLAUDE_CODE_* env.
  • The watch and the sidebar.
  • Skills for commands the user invokes, such as starting a project.
02

Projects

A project is a GitHub Project (v2) owned by the gh-logged-in user. That owner's open projects are the project list. The project's title is its key, for example PAYMENTS_API. No local file names projects.

Items

A user-owned project accepts items only from repos that user owns. So a card is one of two kinds:

  • Native item: an issue or PR from one of the owner's repos.
  • Draft card: everything else. That covers another org's issues and PRs, tracker tickets and one-off steps. The title carries the key or ref, such as PROJ-123: … or acme/api#12: …, and the body holds the link. There is no separate key field.

README and lead settings

The project's README field states its purpose and scope, then a ## Lead settings block. The lead reads the block at start.

Project README
Ship the payments API on the new auth flow.
In scope: the API, its client, the auth bridge.

## Lead settings
lead-repo: acme/payments-api
updates: medium
worker-ends: pr-ready
new-items: issue
issue-repo: acme/payments-api
jira-asks: lead
SettingValuesDefaultMeaning
lead-repoowner/repononeThe repo whose local clone the lead runs in.
updateslow | medium | highmediumHow often the lead posts status updates (§4).
worker-endspr-ready | mergepr-readyWhen a worker's job is over (§7).
new-itemsdraft | issuedraftWhether items the lead creates are draft cards or real issues.
issue-repoowner/repononeWhere issue items are created. The lead asks when it is missing.
jira-askslead | jiraleadWhere a draft card's question goes (§8).

GitHub's own "Default repository" project setting is not readable through the API, so the README carries issue-repo. The user sets the UI default to the same repo so issues added by hand land there too.

Lifecycle

  • Active: a lead is running.
  • Inactive: the board is open and no lead is running.
  • Complete: the board is closed. Closed means done.
  • Deleted: a sidebar action, behind a confirm.
03

The board

The Status field says where each card stands. Its options are fixed, in this order, so every project reads the same way.

StatusMeansLeaves it when
BlockedWaiting on something the watch can't see: another team's change, a deploy window, a doc edit.A person comments on the item or tells the lead.
TodoNot started.The lead starts a worker on it.
In progressA worker is on it.The worker asks, blocks, or puts up a PR.
Needs inputA decision is needed (§8).An answer arrives from someone with write access, or from the user.
In reviewA PR is up, waiting for review and merge. The watch follows it.The PR merges.
DoneThe work is done. With auto-close on, the real issue closes.Archived after 14 days.
  • Abandoned work is removed from the board. No card keeps a status that disagrees with its issue.
  • The tracker's status stays the team's process. A draft card's Done never transitions its ticket.

Who moves cards

  • GitHub's workflows set plain facts on native items: added, PR linked, closed, merged, reopened.
  • A worker sets plainly-true states on its own item through its tools: Needs input, Blocked, In review.
  • The lead moves every draft card and makes every judgment call: reprioritising, and the Blocked and Needs input it raises itself. It sets In progress when it starts a worker.

The template project

Every project starts as a copy of one template, so each has the same Status options, view and workflows. The plugin builds the template once:

  1. Create a project with the Status options above and a Board view grouped by Status.

  2. Mark it as a template with markProjectV2AsTemplate.

  3. The user enables its workflows by hand, once. The API cannot create or configure a workflow; it can only delete one.

Each new project is copyProjectV2 of the template. The template's workflows:

WorkflowSetting
Item added to project→ Todo
Pull request linked to issue→ In review
Item closed→ Done
Pull request merged→ Done
Item reopened→ In progress
Auto-archive itemsDone, after 14 days
Auto-add sub-issues to projectOn
Auto-close issueOn
Review-based workflowsOff

Workflows act only on native items. Draft cards move only when the lead moves them.

04

Status updates and decisions

Status updates carry the project's focus and progress, so a new lead or the sidebar can tell what is happening without a session. The lead posts them through GraphQL createProjectV2StatusUpdate, since gh has no command for them. The update's own status value (On track and the rest) is not used.

updatesThe lead posts
lowOne handoff per sitting.
mediumA post when the focus changes, with decisions folded in.
highA post per decision and per focus change.

A decision that a later reader of the work needs goes on the issue or the tracker ticket, not the project. The project holds progress context only, so deleting a finished project loses nothing needed later.

05

Sessions and roles

Every session has one of three roles: lead, worker or none. The role decides what the session is told and which tools it has, so a plain session stays plain.

Setting the role

A launcher sets the role, the project (its board number) and, for a worker, the item:

Launch settings
--settings '{"env":{"WS_ROLE":"worker","WS_PROJECT":"7","WS_ITEM":"PVTI_…"}}'
  • The env reaches the mod and the session's shell, and is stored in the job's respawnFlags. It survives attach and detach, stop and revive, closing every console, and sending a foreground session to the background.
  • claude --resume keeps it only when the same --settings are passed again, so every revive goes through the plugin's launcher.
  • Launchers strip inherited CLAUDE_CODE_* env. Otherwise a session launched from inside another takes the parent's name.

What the mod does

  • Injects the role's instructions, with the role and project, at session start and again after /clear. It dedupes on a revive.
  • Registers only that role's tools. Role none gets nothing.
  • Reaches other sessions with $.session.send({to, text}), which the recipient sees as a peer message.

Role instructions never read env from the shell, because a shell command containing $VAR always prompts in a background session. The mod injects what the session needs instead.

Skills are only for commands the user invokes, such as starting a project. Plugin skills are visible to every session, so role behaviour never lives in a skill.

06

The lead

The lead drives one project: it decides what runs next, starts and closes workers, and keeps the board and its updates current. It is a plain background session in the local clone of its lead-repo. There is one lead per project and no session above the leads.

Starting a lead

  • Resume: the same session, conversation intact.
  • Refresh: a new session that reads the README, the last few status updates, every card not yet Done with its watched state, and a count of Done cards.

The lead writes as it goes. It moves cards the moment state changes and posts updates per updates. Nothing depends on a final handoff, so a refresh after a crash loses nothing.

The watch

The watch starts with the lead and tells it what changed outside the session, so the lead never polls on its own turn. Each poll reads:

  • The board: cards, statuses and comments on native items.
  • Tracker tickets its cards point to: a Jira search for those keys updated since the last poll.
  • PRs: GitHub GraphQL for linked PRs, plus a title search for each card's key, which finds teammates' and earlier PRs.
  • It reports only changes to the lead.
  • It never watches sessions; the sidebar reads session state from the session layer.
  • It writes its last-seen state to a small local cache that the sidebar reads. The cache is throwaway, not project state.
  • Answers to Needs input items arrive through the watch, and the lead forwards each answer to the waiting worker.

Lead tools

  • Read the board.
  • Add and move cards.
  • Post status updates.
  • Start and close workers.
07

Workers

A worker does one task in one repo. It is a Claude Code team, so its teammates share its worktree. It knows its own item and nothing else about the project.

Launch

The lead launches it in the repo's local clone:

Worker launch
claude --bg -w <branch> -n "<KEY>: <task>" --settings '{"env":{
  "WS_ROLE":"worker","WS_PROJECT":"7","WS_ITEM":"PVTI_…",
  "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS":"1"}}'
  • -w names the branch worktree-<name>, with / as +. The worker renames it to the repo's convention before pushing.
  • A background launch works only in a repo that an interactive claude run has trusted once. When a launch hits this, the lead shows the user the exact command to run.

Brief

The brief comes from the card. The worker holds no project state and never reads the board. Operational questions, such as whether to push now, which labels to use, or draft versus ready PR, are settled by the repo's and the user's own conventions. Those load because the worker runs in the repo.

Worker tools

Each tool is scoped to the worker's own item. The names are proposed.

ToolUseBoard
askA decision is needed. Routed per §8.Needs input
checkAn operational question for the lead, when the conventions are silent or conflict.Unchanged
blockedSays what the worker waits on.Blocked
pr_readyA PR is up for review.In review
doneTells the lead the task is finished.Unchanged; the lead or a workflow sets Done

Permission prompts stay on the worker's own session row, where the user answers them.

End

A worker's job ends at PR ready or at merge, per worker-ends. The lead then closes the worker, which removes the session and its worktree. The branch is already pushed.

08

Questions and blocks

A question goes where its answer belongs, and only people who can change the repo can answer it. That keeps decisions on the record and stops a passer-by from steering the work.

Where ask goes

ItemThe question goes toThe answer comes back through
Native issueA comment on the issueThe watch, then the lead
Draft card with a tracker key, jira-asks: jiraA comment on the tracker ticketThe watch, then the lead
Any other draft cardThe lead's sessionThe lead, from the user

Every route sets Needs input. A draft card can't take comments, which is why its question goes to the lead or the tracker.

Who can answer

  • An answer counts only from someone with write access to the repo: GitHub authorAssociation OWNER, MEMBER or COLLABORATOR.
  • Other comments are read as context only. They never unblock or direct anything.

Blocked

Blocked is for waits the watch can't see. It clears when a person comments on the item or tells the lead. A wait the watch can see, such as review on an open PR, is In review, not Blocked.

Top: projects and sessions

  • Project line: the key and the age of the watch's last poll, or not watched. It shows no project status.
  • Rows: the lead, then its workers, each with live session state: ▶ working; ● needs the user (a permission, a question or an unread reply); ◌ idle.
  • Click: opens the session in the right pane by attaching. Attaching never restarts a session.
  • Other: sessions with no role.
  • Inactive: open boards with no lead. A click starts that project's lead.
  • Complete: closed boards. A click opens one on GitHub, and delete is offered behind a confirm.

Bottom: the open project

  • Its purpose, from the README.
  • Its focus, from the latest status update.
  • The latest state of each watched item.
  • A count of the remaining cards.

Data

The sidebar never polls GitHub or the tracker. It reads the watch's cache and the session layer, so it redraws cheaply and a closed sidebar costs nothing.

10

Setup

Setup is a few one-time steps, so the plugin can create and edit projects and find repos on disk.

  1. Grant the project scope: gh auth refresh -s project.

  2. Fill the plugin's userConfig:

    • a default checkout folder, so repo r resolves to <folder>/r;
    • an optional owner→folder map;
    • the tracker base URL.

  3. Put JIRA_EMAIL and JIRA_API_TOKEN in the environment. The GitHub owner is the gh login.

  4. Let the plugin build the template, then switch its workflows on by hand (§3).

Repo resolution

  • A missing clone is cloned into the folder.
  • A folder whose remote is a different repo is refused.
  • An owner with no mapping and no default folder is refused.
11

Not in this design

Left out

  • A control session. Each lead drives its own project, and the sidebar is the overview.
  • Watching session activity. The session layer already reports it; the watch covers only what sessions can't see.
  • Webhooks. Project webhooks exist only for org-owned projects and would need a public relay.
  • A recent-changes feed. The watch reports changes to the lead; the panel shows current state.
  • Project status on the sidebar. The update's status value is not used, and focus says more.
  • Answers from people without write access. Anyone can comment on a public issue; only people who can change the repo direct its work.

Later options

  • An org-owned project, for native items and comments from org repos.
  • Questions asked on tracker tickets for anyone to answer.
  • Tracker status transitions.
  • An integrated TUI with issue, PR, tracker and board views and an editor pane.
